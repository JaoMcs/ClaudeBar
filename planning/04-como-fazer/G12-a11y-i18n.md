## F19 — VoiceOver

### 1. Rótulo do item da barra

**[CONFIRMADO, teste local]** Montei um app de teste mínimo (SwiftUI `MenuBarExtra` `.menu`, `swiftc -swift-version 6`, `LSUIElement`, ad-hoc) com quatro variantes de label e li o item com System Events (`description`, `title`):

| Variante | Código do label | AXTitle resultante | Visual |
|---|---|---|---|
| A | `Image(...).accessibilityLabel("X")` + `Text("2")` | `X` | ícone + "2" (screenshot) |
| B | `HStack { Image; Text }.accessibilityElement(children: .ignore).accessibilityLabel("X")` | `X` | ícone + "2" (screenshot) |
| C | `Image` + `Text("2").accessibilityLabel("X")` | `X` | — |
| D | `Label("X", systemImage: "exclamationmark.bubble.fill")` | `Comunicar` (nome do símbolo, não o título!) | — |

Conclusões:
- `.accessibilityLabel` no label do `MenuBarExtra` **funciona** e vira o título de acessibilidade do botão da barra, sem mudar o visual. Recomendo a variante B, porque deixa explícito que o conjunto é um só elemento.
- Não use `Label(...)` no label: o VoiceOver leria o nome do SF Symbol.
- `MenuBarExtra("Título", systemImage:)` também define o rótulo de acessibilidade. **[CONFIRMADO]** na doc: "The provided title will be used by the accessibility system." Mas esse init não tem o número ao lado, então não serve aqui.
- Repos que fazem o mesmo (um `Image` com `.accessibilityLabel`) são **[SUPOSIÇÃO]**, mas vão na mesma direção do teste:
  - Clop: https://github.com/FuzzyIdeas/Clop/blob/4be5106951b490c9b61a53f6f15eb580a760bd69/Clop/ClopApp.swift#L1839-L1845 (o comentário diz que sem isso o item é anunciado pelo nome do asset).
  - Awake: https://github.com/mackhaymond/Awake/blob/6705b0b2c3cd2fc0cf054b0982ccca217b1b2353/Sources/Awake/AwakeApp.swift#L131-L142 (rótulo por estado, por extenso).
  - LambdaMonitor: https://github.com/alexlinde/LambdaMonitor/blob/9b8642bbf358e7658d4dc83b06009c7d4b636a51/Sources/App/LambdaMonitorApp.swift#L213-L228 (rótulo com a contagem).

Doc: `accessibilityLabel(_:)` https://developer.apple.com/documentation/swiftui/view/accessibilitylabel(_:) (macOS 13+). `accessibilityElement(children:)` https://developer.apple.com/documentation/swiftui/view/accessibilityelement(children:).

Texto proposto, montado a partir do que o store já sabe (`openSessionCount`, `barState`), sem estado novo:
- `"ClaudeBar: 2 sessions, one waiting for you"`. Se contar quantas esperam exigir um getter novo em `SessionMerge`, comece com `"ClaudeBar: 2 sessions, waiting for you"`, que já usa o `barState`. O plural de "sessions" vai num `.stringsdict` (ver F21).

### 2. Linhas do menu sem depender de emoji

**[CONFIRMADO, teste local]** No mesmo app de teste, abri o menu via AX e li o `title` de cada item:
- `Menu("⏳  emoji-row — working")` → AXTitle `"⏳  emoji-row — working"`. O emoji entra no texto falado, e o VoiceOver diz o nome dele em voz alta (o nome exato falado é **[SUPOSIÇÃO]**, não liguei o VoiceOver).
- `Menu { … } label: { Label("lbl-row — working", systemImage: "ellipsis.circle") }` → AXTitle `"lbl-row — working"`, e o screenshot mostra o SF Symbol à esquerda (macOS 26).
- `.accessibilityLabel("…")` aplicado num `Menu` dentro do `MenuBarExtra(.menu)` foi **ignorado**: o AXTitle continuou sendo o texto visível. Ou seja, no estilo `.menu` o que o VoiceOver fala é o próprio texto da linha. A linha precisa se explicar em palavras, porque não dá para pôr um rótulo separado.

Recomendação (ponytail): trocar `icon(for:)` (emoji) por `Label(texto, systemImage: …)` usando SF Symbols. O texto da linha já contém o estado por extenso ("waiting for you"), então ele sozinho é acessível. O ícone vira decoração.
- **[SUPOSIÇÃO]** No macOS 14/15, menus SwiftUI podem não mostrar o ícone do `Label` (no 26 mostram, como confirmado acima). Mesmo assim o título continua correto, então nada se perde.
- `[subagente]` → texto, ok como está (vira string localizável).

### 4. Anúncio quando o popup (HUD) aparece

API, toda **[CONFIRMADA]**:
- `NSAccessibility.post(element: Any, notification: NSAccessibility.Notification, userInfo: [NSAccessibility.NotificationUserInfoKey: Any]?)`, macOS 10.7+. https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/post(element:notification:userinfo:)
- `.announcementRequested`: "If VoiceOver is enabled, it's presented via speech and/or braille. Otherwise, it does nothing." Exige `userInfo` com a chave `.announcement`. https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/notification/announcementrequested
- `.announcement` (string localizada) e `.priority`. https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/notificationuserinfokey/priority
- Header do SDK (`AppKit/NSAccessibilityConstants.h`, Xcode local):
  - sobre `NSAccessibilityAnnouncementRequestedNotification`: "This notification should be posted for the application element."
  - sobre `NSAccessibilityPriorityKey`: "This key is required for NSAccessibilityAnnouncementRequestedNotification."
  - `NSAccessibilityPriorityLow = 10, Medium = 50, High = 90`.
  - Valores aceitos no userInfo: "NSString, NSNumber, NSArray, NSValues…". Por isso a prioridade vai como `.rawValue`.
- Alternativa SwiftUI, macOS 14+: `AccessibilityNotification.Announcement(String | AttributedString).post()`, do framework `Accessibility`. A prioridade vai via `AttributedString.accessibilitySpeechAnnouncementPriority`. https://developer.apple.com/documentation/accessibility/accessibilitynotification/announcement. A assinatura `public func post()` foi conferida no `.swiftinterface` do SDK local.

Código sugerido, dentro de `StatusHUD.show(...)`, que já é `@MainActor` (então sem problema de concorrência no Swift 6):

```swift
NSAccessibility.post(
    element: NSApp as Any,
    notification: .announcementRequested,
    userInfo: [
        .announcement: "\(alert.title). \(body)",
        .priority: NSAccessibilityPriorityLevel.high.rawValue,
    ]
)
```

Repos que fazem isso (**[SUPOSIÇÃO]**, código de terceiros):
- Thaw, app de barra de menu, posta em `NSApplication.shared` com prioridade medium: https://github.com/thaw-app/Thaw/blob/81b9474c8f673fbb8ed191590554b354ce355110/Thaw/Utilities/AccessibilityAnnouncements.swift
- FineTune, HUD em `NSPanel`, posta no próprio painel: https://github.com/ronitsingh10/FineTune/blob/2285279d36d3f8115c1c2d4aecd904f1bdf96a51/FineTune/Views/HUD/HUDWindowController.swift#L344-L354

**Armadilha principal, [SUPOSIÇÃO] por relatos na lista accessibility-dev da Apple (não consegui abrir as páginas, HTTP 502; resumo vindo da busca):**
- Um engenheiro do VoiceOver teria dito que o VoiceOver só escuta anúncios da janela ativa da frente: https://lists.apple.com/archives/accessibility-dev/2016/Jan/msg00006.html
- Um dev de app de barra de menu relatou que o anúncio só funcionava com o app ativo e uma janela visível: https://lists.apple.com/archives/accessibility-dev/2016/Jan/msg00003.html
- Postar só em `NSApp` não teria funcionado em 2015: https://lists.apple.com/archives/accessibility-dev/2015/Jul/msg00028.html
- O ClaudeBar é `.accessory` e o HUD é `.nonactivatingPanel` de propósito (não rouba foco). **Então pode ser que o VoiceOver não fale nada.** Não testei com o VoiceOver ligado, porque mudar o estado de acessibilidade do sistema é ação do usuário.
- Como testar (o usuário faz): ligar o VoiceOver (Cmd+F5), deixar outro app em foco, disparar "Ver exemplo de popup" e conferir se fala. Repetir postando em `NSApp` e em `panel`, e ficar com o que falar.
- Se nenhum dos dois falar:
  - Alternativa 1: `AVSpeechSynthesizer`. Ignora as preferências do VoiceOver e fala mesmo para quem não usa VoiceOver, então teria que checar `NSWorkspace.shared.isVoiceOverEnabled` antes. É mais código. Só vale se o teste falhar.
  - Alternativa 2: aceitar a limitação. A informação continua no rótulo da barra (item 1), que o VoiceOver lê quando o usuário navega até ele.
- Bônus barato: o `HUDView` ganha `.accessibilityElement(children: .combine)` para ficar legível se o usuário navegar até o painel.

## F21 — Inglês + português

### Decisão de formato: `.strings` + `Bundle.main`, copiados à mão (recomendado)

Por que **não** `Package.swift` com `defaultLocalization` + `resources: [.process(...)]` + `Bundle.module`:
- **[CONFIRMADO]** Com `resources`, o SwiftPM gera um `ClaudeBar_ClaudeBar.bundle` ao lado do binário, e o `Bundle.module` gerado procura nesse lugar.
- **[SUPOSIÇÃO]**, relato em código de terceiros: o CodexBar remenda o acessor por causa do "fatal trap in the autogenerated `Bundle.module` when the resource bundle is not placed at the bundle root". A raiz do `.app` não é lugar de recurso, e colocar coisa ali quebra a assinatura. https://github.com/steipete/CodexBar/blob/main/Scripts/package_app.sh (linhas ~147-181).
- Resultado: o app empacotado à mão teria que copiar o `.bundle` e ainda correria risco de crash. `Bundle.main` + `.lproj` direto em `Contents/Resources` é o layout nativo de app macOS, sem mexer no `Package.swift`.
- **[SUPOSIÇÃO]** Se puser `.lproj` dentro de `Sources/ClaudeBar/` sem declarar, o SwiftPM avisa sobre arquivos "unhandled". Por isso: **pasta `Resources/` na raiz** (a mesma que o G13 propõe para o `AppIcon.icns`).

Referência open source do mesmo padrão (copiar `Resources/.` para `Contents/Resources`), **[SUPOSIÇÃO]** (código de terceiros):
- https://github.com/steipete/CodexBar/blob/main/Scripts/package_app.sh, em torno da linha 605: `cp -R "$APP_RESOURCES_DIR/." "$APP/Contents/Resources/"`. O `Resources` deles tem `en.lproj/Localizable.strings` e `.stringsdict`, segundo `Scripts/check-app-locales.mjs`.
- O CodexBar também tem seletor de idioma dentro do app (`Sources/CodexBar/Localization.swift`, com cache e lock). **Não copiar**: é YAGNI para dois idiomas que seguem o Mac.

Por que não String Catalog (`.xcstrings`):
- **[CONFIRMADO]** `xcrun xcstringstool compile` existe com o Xcode local.
- **[SUPOSIÇÃO]** Ele não vem nas Command Line Tools sozinhas, e o catálogo exigiria um passo de compilação no `build-app.sh`. `.strings` + `.stringsdict` funcionam sem compilar (testado abaixo). Fica para quando houver mais de 2 idiomas.

### Teste local (scratchpad, sem tocar no repo)

App mínimo `T.app` com `Contents/Resources/{en,pt-BR}.lproj/Localizable.strings`, `CFBundleDevelopmentRegion=en`, `swiftc -swift-version 6`, ad-hoc (`codesign --verify --strict` ok). Sistema com `AppleLanguages = ("pt-BR")`, `AppleLocale = pt_BR`.

| `-AppleLanguages` | `preferredLocalizations` | `Locale.current` | `String(localized: "Quit ClaudeBar")` | `"\(n) sessions open"` | Relativo (sem locale fixo) |
|---|---|---|---|---|---|
| (sistema) | `pt-BR` | `pt_BR` | Sair do ClaudeBar | 2 sessões abertas | há 2 min. |
| `en` | `en` | `en_BR` | Quit ClaudeBar | 2 sessions open | 2 min ago |
| `fr` | `en` (fallback) | `en_BR` | Quit ClaudeBar | 2 sessions open | 2 min ago |
| `pt-PT` | `pt-BR` | `pt_BR` | Sair do ClaudeBar | 2 sessões abertas | há 2 min. |
| binário solto (`swift run`) | `en` | `pt_BR` | Quit ClaudeBar | 2 sessions open | há 2 min. |

Tudo **[CONFIRMADO]** nesta máquina. Conclusões:
1. **Basta remover o `Locale(identifier: "pt_BR")`.** Dentro do `.app`, `Locale.current` acompanha o idioma que o bundle resolveu (`en_BR` quando cai em inglês), então datas relativas e textos ficam no mesmo idioma.
2. **`CFBundleDevelopmentRegion` precisa virar `en`.** Testei manter `pt_BR` com o Mac em `fr`: o texto saiu em pt-BR e `Locale.current` em `en_BR`, ou seja, idiomas misturados. Com `en`, o fallback é inglês. Doc **[CONFIRMADO]**: "The system uses this key as the language if it can't locate a resource for the user's preferred language." https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundledevelopmentregion
3. **Nome da pasta: `pt-BR.lproj`**, com hífen, como no formato da doc acima e na doc "Localizing package resources" (https://developer.apple.com/documentation/xcode/localizing-package-resources). Funcionou no teste.
4. **Chave = texto em inglês.** Assim o `swift run`, os testes (`Bundle.main` sem `.lproj`) e qualquer chave faltando mostram inglês legível. Único efeito colateral no `swift run`: data relativa em pt com texto em inglês. É só dev, aceitável.
5. **Interpolação vira formato na chave**: `String(localized: "\(n) sessions open")` procura `"%lld sessions open"`. `Int` → `%lld`; `String` → `%@`.
6. **Plural com `.stringsdict`** (mesmo nome, `Localizable.stringsdict`, no `pt-BR.lproj` e no `en.lproj`): testado, com `n=1` sai "1 sessão aberta" e com `n=2` sai "2 sessões abertas". Vale só para o rótulo de acessibilidade da barra e para o que tiver contagem.
7. `plutil -lint` valida `.strings` e `.stringsdict`. Ad-hoc + recursos copiados **antes** do `codesign` = assinatura válida (o G13 já confirmou a ordem).
8. `CFBundleLocalizations` / `CFBundleAllowMixedLocalizations` **não são necessários**: o teste funcionou sem eles. As docs descrevem outra coisa ("localizations handled manually" e "retrieval of localized strings from frameworks"). https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundlelocalizations

### Que APIs usar no código

- **SwiftUI `Text("literal")`, `Button("literal")`, `Toggle("literal", …)`, `Menu("literal")`**: o literal já é `LocalizedStringKey` e procura em `Bundle.main`. **Basta trocar o literal pt-BR pelo inglês** e pôr a tradução em `pt-BR.lproj`. **[CONFIRMADO]** pela doc de `String(localized:…)`: "If nil, an app searches its main bundle." Que o `LocalizedStringKey` do SwiftUI usa `Bundle.main` por padrão é **[SUPOSIÇÃO]** bem estabelecida. Não testei SwiftUI com `.lproj` (o teste foi com `String(localized:)`).
- **Strings fora de view** (`Alert.title`, `SessionTerminator.actionTitle`, `label(for:)`, `NSAlert`): `String(localized: "…")`. **[CONFIRMADO]**: `init(localized:table:bundle:locale:comment:)` existe no macOS 12+, e `bundle: nil` usa o main bundle. **Não passar `bundle:`.** O default já é o `Bundle.main`, então é desnecessário.
- **Variável passada a `Text(variavel)`** (ex.: `Menu(label(for: row))` com `String`) **não é traduzida**: `Text(String)` usa a string literalmente. Por isso `label(for:)` precisa montar o texto já traduzido com `String(localized:)`. **[SUPOSIÇÃO]**: é o comportamento documentado de `Text.init<S: StringProtocol>`, mas não reli a doc.
- `String(localized: "KEY", defaultValue: "…")` existe **[CONFIRMADO]**, mas é desnecessário se a chave já for o texto em inglês.
- `locale:` em `String(localized:)` **não** escolhe o idioma da tradução. **[CONFIRMADO]**: "This doesn't change which locale the system uses to look up the localized string."
- Mensagem do Claude no popup (`message` do hook Notification) **não se traduz**: vem pronta do Claude Code. **[CONFIRMADO]** na doc dos hooks, o payload tem `message`, `title` (opcional) e `notification_type` (https://code.claude.com/docs/en/hooks.md#notification-input). O setting `language` do Claude Code afeta as respostas do Claude, não esses textos (https://code.claude.com/docs/en/settings-reference.md#language). Se esses textos mudam de idioma é **[SUPOSIÇÃO]**, não testado.
- Logs `OSLog` em pt-BR: **não traduzir** (não são UI).
