## F19 — VoiceOver + legenda dos estados

### Objetivo

Quem usa VoiceOver precisa saber, sem enxergar o símbolo:
1. o que é o item da barra, quantas sessões estão abertas e qual é o estado;
2. o estado de cada linha do menu, sem ouvir o nome de um emoji;
3. que um popup apareceu.

Quem enxerga ganha uma legenda dos 4 símbolos dentro do próprio menu, que hoje só o README explica.

### Decisão técnica e por quê

1. **Item da barra**: `HStack { Image; Text }` com `.accessibilityElement(children: .ignore)` e `.accessibilityLabel(...)`. O texto vem de `BarState`, sem estado novo no store. Na pesquisa (variante B), essa foi a forma que mudou o `AXTitle` sem mudar o visual. Confirmei de novo aqui, com o texto traduzido.
   - Descartado `Label(...)` no label da barra: o VoiceOver lê o nome do SF Symbol ("Comunicar").
   - Descartado `MenuBarExtra("título", systemImage:)`: esse init não mostra o número.
   - Descartado `.accessibilityLabel` só no `Image`: funciona, mas deixa dois elementos e o número continua lido à parte.
2. **Texto sem plural**: `"ClaudeBar. Sessões: 2. Claude está esperando você"`.
   - Descartado "2 sessões, 1 esperando você" (BACKLOG): exige `.stringsdict` em dois idiomas e um getter novo para contar quantas esperam. O estado agregado já diz o que importa.
   - Descartada a concordância automática (`^[…](inflect: true)`): o suporte a pt-BR não foi confirmado.
3. **Linhas do menu**: o emoji sai e entra `Label(texto, systemImage:)`. O texto da linha já diz o estado por extenso, e é ele que o VoiceOver lê. No estilo `.menu`, `.accessibilityLabel` no item é **ignorado** (pesquisa, CONFIRMADO).
   - Descartado `.accessibilityLabel` por linha: não tem efeito no estilo `.menu`.
   - Descartado manter o emoji e tirá-lo do texto: o único lugar onde ele aparece é o próprio texto.
4. **Símbolo da linha = símbolo da barra para o mesmo estado** (`BarState.x.symbolName`). Assim a legenda vale para as duas coisas.
   - Descartado `symbolName` em `SessionState`: ele mora em `ClaudeBarCore`, que o hook também usa, e símbolo é coisa de UI.
5. **Legenda**: um submenu "O que os ícones significam" com `ForEach(BarState.allCases)`. `CaseIterable` resolve, sem tipo novo. Os itens ficam cinza porque não têm ação, o que é aceitável para uma legenda.
   - Descartada uma janela ou um popover de ajuda: é mais código e precisa de foco.
6. **Anúncio do popup**: `NSAccessibility.post(element: NSApplication.shared, notification: .announcementRequested, userInfo: [.announcement:, .priority: high.rawValue])`, dentro de `StatusHUD.show`. O header do AppKit manda postar no elemento da aplicação. `StatusHUD` é `@MainActor`, então não há problema de concorrência. Só o caminho do popup próprio anuncia: a notificação nativa o VoiceOver já lê.
   - Descartado `AccessibilityNotification.Announcement(...).post()`: o efeito é o mesmo e traz `import Accessibility` sem ganho.
   - Descartado `AVSpeechSynthesizer`: ignora as preferências do VoiceOver e fala para quem não usa VoiceOver. Só entra se o teste manual provar que o anúncio não sai, e mesmo assim como task separada.
7. **`HUDView` com `.accessibilityElement(children: .combine)`**: se o usuário navegar até o painel, título e corpo são lidos juntos. Custa uma linha.
8. **Textos do F19 em pt-BR, como o resto do código hoje.** A pesquisa sugeria escrever já em inglês com `String(localized:)`. Descartei isso: entre o F19 e o F21 a UI ficaria metade em inglês e metade em português, e as outras tasks (F05, F07, F11, F20, F22, F24) também escrevem em pt-BR. O F21 vai precisar de uma varredura completa de qualquer jeito. Converter as 6 strings do F19 nessa varredura custa minutos.

```swift
    /// Texto da linha. Diz o estado por extenso: é o que o VoiceOver lê, e no
    /// estilo `.menu` um `.accessibilityLabel` no item é ignorado.
    static func label(for row: SessionRow, now: Date = Date()) -> String {
        var text = row.isSubagent ? "[subagente] " : ""
        text += "\(row.name) — \(description(for: row.state))"
        if let updatedAt = row.updatedAt {
            text += " (\(relativeFormatter.localizedString(for: updatedAt, relativeTo: now)))"
        }
        return text
    }

    /// O mesmo símbolo da barra para o mesmo estado, então a legenda vale
    /// para as linhas também.
    private static func symbolName(for state: SessionState) -> String {
        switch state {
        case .working: BarState.working.symbolName
        case .idle: BarState.done.symbolName
        case .waiting: BarState.waiting.symbolName
        }
    }

    private static func description(for state: SessionState) -> String {
        switch state {
        case .working: "processando"
        case .idle: "pronto"
        case .waiting: "aguardando você"
        }
    }
```

## F21 — Inglês + português

### Objetivo

O app segue o idioma do Mac: português para quem usa `pt-BR` (e também `pt-PT`, que cai em pt-BR), inglês para qualquer outro idioma. As datas relativas ficam no mesmo idioma do texto.

### Decisão técnica e por quê

1. **`.strings` em `Resources/{en,pt-BR}.lproj/`, na raiz, lidos via `Bundle.main` (o default) e copiados pelo `build-app.sh` antes do `codesign`.** É o layout nativo de app macOS e não mexe no `Package.swift`. O G13 confirmou que o SwiftPM ignora `Resources/`, e o protótipo compilou sem warning.
   - Descartado `defaultLocalization` com `.process` e `Bundle.module`: gera um `.bundle` à parte que o empacotamento manual teria que copiar e assinar, com relato de crash quando ele não fica na raiz.
   - Descartado String Catalog (`.xcstrings`): exige `xcstringstool` no build, e não está confirmado que ele vem só com as Command Line Tools.
   - Descartado seletor de idioma dentro do app: YAGNI para dois idiomas que seguem o Mac.
2. **A chave é o texto em inglês.** No `swift run`, nos testes e quando faltar uma chave, o que aparece é inglês legível. Os testes ficam determinísticos, porque no `swift test` o `Bundle.main` é o runner e não tem `.lproj`.
3. **`en.lproj/Localizable.strings` fica vazio, só com um comentário.** Ele existe para o macOS saber que o app fala inglês e cair nele com o Mac em francês. Testado aqui: o texto e as datas saem em inglês.
   - Descartado `en.lproj` duplicando chave = valor: são 35 linhas que não dizem nada.
   - Descartado ficar sem `en.lproj`: sem ele, o único idioma disponível seria o pt-BR e o fallback não teria para onde ir. Não testei esse caso porque o vazio já resolve.
4. **`CFBundleDevelopmentRegion = en`.** Com `pt_BR`, o Mac em francês mistura texto em pt e datas em inglês (pesquisa, CONFIRMADO).
5. **Remover `formatter.locale = Locale(identifier: "pt_BR")`.** No `.app`, o `Locale.current` acompanha o idioma resolvido (`en_BR` quando cai em inglês).
6. **APIs:**
   - Literal em `Text`, `Button`, `Toggle` e `Menu`: basta trocar o texto pt pelo inglês, porque o `LocalizedStringKey` procura no `Bundle.main` (CONFIRMADO aqui).
   - String montada fora de view, ou passada como variável: `String(localized:)`, sem `bundle:`.
   - `Text(variavel)` **não** traduz (CONFIRMADO). Por isso `label(for:)`, `title` e `actionTitle` já devolvem o texto traduzido.
7. **Número que não é quantidade (PID) entra como `String(pid)`**, para não sair "kill 4.321" (CONFIRMADO). `errno` é pequeno e fica `%d`. A contagem da barra fica `%lld`.
8. **Caminho e id ficam fora da chave.** O `cwd` do `NSAlert` passa a ser concatenado fora do texto traduzido. Uma chave com caminho nunca seria encontrada.

import Foundation
import Testing

@testable import ClaudeBar

/// No `swift test` o `Bundle.main` é o runner, sem `.lproj`: as tabelas são
/// lidas direto de `Resources/`, que é o que o `build-app.sh` copia.
private let resources = URL(fileURLWithPath: #filePath)
    .deletingLastPathComponent()
    .deletingLastPathComponent()
    .deletingLastPathComponent()
    .appendingPathComponent("Resources")

private func table(_ language: String) throws -> [String: String] {
    let url = resources.appendingPathComponent("\(language).lproj/Localizable.strings")
    let data = try Data(contentsOf: url)
    let plist = try PropertyListSerialization.propertyList(from: data, format: nil)
    return try #require(plist as? [String: String])
}

/// `%@`, `%lld`, `%d`… na ordem em que aparecem.
private func specifiers(_ text: String) -> [String] {
    text.matches(of: /%(@|l{0,2}d)/).map { String($0.output.0) }
}

@Suite("Tradução")
struct LocalizationTests {
    @Test func tabelaEmPortuguesTemOsMesmosMarcadoresDaChave() throws {
        let pt = try table("pt-BR")
        #expect(!pt.isEmpty)
        for (key, value) in pt {
            #expect(specifiers(key) == specifiers(value), "\(key)")
            #expect(!value.isEmpty, "\(key)")
        }
    }

    /// Em inglês a chave já é o texto; a tabela só precisa existir e ser válida.
    @Test func tabelaEmInglesEhValida() throws {
        _ = try table("en")
    }

    /// Os textos que o código monta sozinho têm tradução — sem ela, o menu
    /// misturaria inglês no meio do português.
    @MainActor
    @Test func textosDosEstadosEAvisosTemTraducao() throws {
        let pt = try table("pt-BR")
        let titulos = BarState.allCases.map(\.title) + [Alert.finished.title, Alert.waiting.title]
        for titulo in titulos {
            #expect(pt[titulo] != nil, "sem tradução: \(titulo)")
        }
    }
}

### O que NÃO fazer

- Não interpolar PID, id ou caminho como número ou dentro da chave: use `String(pid)` e deixe o caminho fora.
